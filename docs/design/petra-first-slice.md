# PETRA 첫 구현 계획

상태: 2026-10-09 설계 초안. 기준 main `823d823`과 [설치 설계](petra-installation.md), [수용 계획](petra-acceptance.md)을 구체화한다. 아래 기능과 시나리오는 아직 구현하거나 실행하지 않았다.

## 1. 첫 번째로 확인할 것

**쇼핑몰 코드와 문서는 루트에 있고, PETRA는 안쪽에 있어도 두 에이전트가 서로의 작업을 읽는다.**

첫 구현은 완성된 설치·이전 제품이 아니다. 폐기 가능한 로컬 쇼핑몰과 bare 원격, solp·amazon 두 clone으로 작은 소비 배치를 검증한다. 실제 기존 프로젝트에는 적용하지 않는다. generic installer나 새 협업 프로토콜을 먼저 만들지 않는다.

완료를 판단할 질문은 셋이다.

1. 사용자는 루트 README에서 쇼핑몰 실행 방법을 찾고 PETRA 안내는 별도로 찾을 수 있는가?
2. 새 Codex·Claude 세션이 공통 계약을 실제로 읽고, 시작/작업/종료 흐름을 수행하는가?
3. 기록 경로가 달라도 동료의 질문·변경·파일 겹침을 기존 의미대로 전달하는가?

## 2. 코드와 배포 위치

제작 저장소의 소스는 우선 현 위치를 유지한다. 하나의 구현을 배포 목록으로 임시 소비 배치에 복사하며, 제작 저장소에 동일 코드를 `.petra/runtime/`로 중복 커밋하지 않는다. 배포 후 검색·치환으로 다른 실행 정책을 만드는 것도 금지한다.

| 제작자 소스 또는 입력 | 소비 프로젝트의 목표 위치 | 규칙 |
|---|---|---|
| 새 `bin/petra` 진입점 | `.petra/bin/petra` | 얇은 명령 전달과 위치 확인. 협업 판정은 기존 공통 코드에 유지 |
| `scripts/collab.sh` | `.petra/runtime/scripts/collab.sh` | 기존 명령 의미 유지 |
| `harness/hooks/*.sh` | `.petra/runtime/harness/hooks/` | 현재 훅을 재사용. 도구별 판정 복제 없음 |
| `harness/attach-sobaya.sh`, `harness/sobaya-installed.sh`, `harness/sobaya/installed-lib.sh` | `.petra/runtime/harness/`와 그 아래 `sobaya/` | root pin과 legacy lock은 이동하지 않음 |
| `harness/sobaya/collab-dispatch.sh` | `.petra/runtime/harness/sobaya/` | 패키지 안에 있다고 외부 복사본도 갱신됐다고 간주하지 않음 |
| `collab/templates/`의 빈 양식 | `.petra/templates/` | 실제 claim·저널·검토 기록은 제외 |
| 전용 소비자 문서·설정 템플릿 | `.petra/README.md`, `.petra/AGENTS.md`, 초기 `.petra/config.sh` | 제작자 AGENTS 전체 복사 금지. config는 생성 뒤 프로젝트 소유 |
| 기존 3개 스킬의 전용 진입점 | `.agents/skills/petra-*/` | 본문은 PETRA 절차 참조. 사용자 스킬·Claude 설정 전체 교체 금지 |
| `.githooks/`의 관리 진입점 | 루트 `.githooks/` | 주소·파일 종류·실패 전달 유지, 내부 호출만 PETRA로 변경 |
| 소비자용 PR 구역·workflow·도구 설정 템플릿 | 루트의 기존 공유 파일 내 관리 영역 | 기존 앱 CI와 설명 보존. 승인된 항목만 병합 |
| PETRA 버전·출처·관리 파일 기준 | `.petra/manifest.json` | 패키지 제작 시 생성. 제작자 VERSION은 배포 버전 입력일 뿐 소비본에 중복 기준으로 두지 않음 |

현재 `init.sh`, `install-into.sh`의 전체 복사·전역 치환·lock 삭제는 새 설치 내부에서 호출하지 않는다. 테스트, fixture, 설계/검토 보고서, 실제 협업 기록, 자동 GitHub 정책 변경은 기본 배포에 넣지 않는다. source 배포의 정확한 파일 목록과 제외 검사는 구현 PR의 테스트 입력으로 리뷰한다.

### 위치를 섞지 않는 최소 계약

- `ROOT`: 명령이 실제로 적용될 Git 프로젝트. 명시한 대상이나 확인된 Git 루트로 결정하며 잘못된 호출자 환경에 끌려가지 않는다.
- `RUNTIME_ROOT`: 로컬에서 실행 중인 PETRA 코드 위치. lib를 읽는 기준이지 프로젝트 데이터를 찾는 기준이 아니다.
- 기록 경로: 현재 및 원격 ref별 manifest의 `records`. 새 설치는 `.petra/collab`, 이전 대상은 기존 `collab`. manifest가 없는 구형 ref만 fallback한다.
- `CACHE`: worktree별 Git 메타데이터 안의 `petra/`. package와 협업 기록은 cache가 아니다. cache 삭제 후에도 미응답 질문을 다시 읽을 수 있어야 한다.

이 네 경계를 먼저 분리하고 `dirname`과 `collab/` 문자열을 일괄 치환하지 않는다. 로컬 프로젝트 config와 원격 manifest의 신뢰도는 다르다. 원격 ref의 shell 코드/config를 실행하지 않는다.

## 3. 첫 쇼핑몰 시나리오

앱은 고정 fixture이며 실제 서비스 배포, 결제, 비밀값, GitHub 리포 생성은 없다. 자동 테스트의 구체적인 파일과 worker 입력은 별도로 검토한다.

| 순서 | 상황 | 관찰할 결과 |
|---|---|---|
| 1 | 임시 쇼핑몰 루트에 README·AGENTS·app·tests가 이미 있음 | 작은 소비 배치를 붙여도 원래 앱 파일은 보존. 실제 claim/저널은 빈 상태에서 시작 |
| 2 | solp는 Codex, amazon은 Claude로 각각 새 세션 | 도구 버전을 기록. PETRA 계약을 실제 소비하고 최초 join 안내 후 digest 수행. 반대 도구 조합은 후속 교차 검증 |
| 3 | solp는 상품 목록, amazon은 장바구니 작업 선언 | 각각의 goal과 브랜치가 보이고 디렉터리 소유권으로 영역을 통째로 잠그지 않음 |
| 4 | solp가 공용 가격 함수의 계약 변경을 저널로 push | 그 함수를 쓰는 amazon의 에이전트가 다음 동기화에서 변경을 읽고 호출부를 확인. 제목만 나열하지 않음 |
| 5 | amazon이 ask @solp로 질문하고 solp가 reply | 수신자에게 질문이 전달되고 답변 전에는 처리됐다고 숨기지 않음. 캐시 재생성 후에도 미응답 질문 확인 |
| 6 | 둘이 같은 허브 파일을 편집하려 함 | 최신 스냅샷 기준 편집 겹침을 알림/차단. 서로 다른 파일이면 오보 없음. 오프라인·오래된 정보는 안전하다고 표시하지 않음 |
| 7 | 구형 collab 경로를 가진 테스트 ref도 남아 있음 | 새 도구가 두 기록 배치를 읽되 같은 이벤트를 중복 주입하지 않음. 구형 도구가 새 배치를 이해한다고 주장하지 않음 |
| 8 | 기능 작업을 마무리하고 handoff·check·PR 본문 생성 | 기록 위치가 바뀌어도 질문·검증·남은 일이 보존되고 사라진 scripts/harness 경로를 호출하지 않음 |

검사는 즉시 실시간 통신을 보장하지 않는다. 명시적 pulse/digest 또는 지원이 확인된 훅의 주기 이후 관찰 결과를 기록한다. 지원하지 않는 자동 훅은 수동 CLI로 구분하며 같은 수준의 자동 편집 보호라고 쓰지 않는다.

실제 세션은 비용·연결 범위를 확인한 뒤 실행한다. 사용할 수 없는 도구는 NOT RUN/BLOCKED로 기록한다. CLI fixture만 통과한 상태를 Codex·Claude 지원 완료로 표시하지 않는다.

## 4. 이번에 하지 않을 것

- 실제 소비 프로젝트의 구형 배치 이전과 기존 저널 재작성.
- Sobaya 설치 방식 변경, 버전 bump, 테스트 자동 승인, 진행 상태의 버전 간 재개.
- 기존 승인된 191개 테스트의 임의 수정. 새 배치 대응 입력이 필요하면 별도 초안을 승인받는다.
- 새 상주 프로세스·서버·메시지 저장소·스킬 종류·일상 훅 추가.
- 모든 사용자 Git 훅과 설정을 자동으로 병합하는 범용 프레임워크.
- 정식 배포나 이슈 #4 완료 처리.

## 5. 검토와 다음 단계

첫 구현의 코드 변경은 경로 경계, 작은 배포 목록, 진입점 연결에 한정한다. 실행 판정의 무관한 리팩터링과 Git 이력 재작성은 하지 않는다. 초기 증거는 커밋·OS·도구 버전·명령·관찰·실패/미실행으로 기록한다.

첫 시나리오가 확인되면 같은 구현에 설치 계획/적용·join·verify를 붙인다. 그 다음 구형 이전·업데이트·실패 복구를 구현한다. 각 단계는 별도 검토 단위이며, 첫 시나리오가 안 돌아가면 설치 기능을 더 쌓기 전에 원인을 고친다.
