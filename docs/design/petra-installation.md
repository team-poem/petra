# PETRA 설치 구조와 이전 설계

상태: 구현 기준 제안. solp의 설계 요청으로 작성했으며 팀의 최종 승인과 구현은 별도다.
작성일: 2026-10-07. 기준: main `1ebbf5f`, PR #5 검토본 `9d8019d`.
관련: [이슈 #4](https://github.com/team-poem/poem-collaboration-harness-template/issues/4), [PR #5](https://github.com/team-poem/poem-collaboration-harness-template/pull/5).

이 문서의 구조와 명령은 **목표 설계이며 현재 실행 가능한 사용 안내가 아니다.** 이번 브랜치는 문서만 추가한다. PR #5의 호환성 수정과 머지 후 실제 반영된 코드를 다시 확인하고 구현한다.

## 1. 무엇을 해결하는가

쇼핑몰을 만들려고 설치했는데 README는 협업 하네스를 설명하고, `scripts/`, `tests/`, `docs/`에는 쇼핑몰과 하네스의 파일이 섞인다. PETRA를 고치려는 것인지 쇼핑몰을 고치려는 것인지 사람이 구분하기 어렵다.

**결정: 프로젝트가 최상위의 주인이고 PETRA는 프로젝트에 설치되는 협업 도구다.**

- 이름: PETRA, Poem's Engineering, Testing & Review Assistant. 이슈에서 solp와 amazon이 선호한 명칭을 사용한다. 저장소 URL 변경은 하지 않는다.
- 실행 코드와 사용 안내를 `.petra/` 아래로 모은다. 프로젝트 코드의 `src/`, `app/`, `apps/` 구조나 Git 루트는 옮기지 않는다.
- 설치는 필요한 파일과 연결만 추가한다. npm 의존성, 상주 프로세스, 새 서버, 새 협업 채널은 추가하지 않는다.
- PETRA 업데이트와 프로젝트 설정 변경, Sobaya 업데이트를 서로 다른 작업으로 취급한다.
- 기존 claim, 저널, WIP ref, PR 승인 절차의 의미를 바꾸지 않는다. 충돌을 완전히 없앤다고 약속하지 않는다.

| PR #5 `installed-lib.sh` | Sobaya 전달 훅이 원본 `.githooks`를 가리키는지 검사 | 루트 `.githooks` 연결 주소를 유지하고 안쪽 구현만 옮긴다 |

## 3. 설치 후 모습

신규 프로젝트의 목표 배치다. 도구별 연결 파일은 사용하고 검증된 도구에 대해서만 설치한다.

```text
shop/
  README.md                    쇼핑몰의 목적, 실행, 테스트 안내
  AGENTS.md                    쇼핑몰 규칙과 실제 Test: 명령, PETRA 참조
  src/                         쇼핑몰 코드: PETRA가 옮기지 않음
  package.json
  .petra/
    README.md                  사람용 협업 안내
    AGENTS.md                  에이전트용 공통 협업 계약
    bin/petra                  기존 협업 명령으로 연결하는 작은 진입점
    runtime/                   협업 CLI, 훅, 설치기, Sobaya 어댑터 구현
    templates/                 새 claim·저널의 빈 양식
    config.sh                  프로젝트가 소유하는 협업 설정
    manifest.json              설치 버전·출처·관리 파일의 기준 정보
    collab/                    이 프로젝트의 claim·저널
  .agents/skills/petra-*/       기존 3개 절차의 이름이 겹치지 않는 진입점
  .claude/                     필요한 연결만 병합, 기존 설정 보존
  .codex/                      실제 지원 확인된 연결만 병합
  .githooks/                   공용 Git 훅 진입점, 실제 처리는 PETRA로
  .github/workflows/           앱 CI와 소비자용 협업 검사
  sobaya.json, sobaya.lock     설치형 Sobaya를 선택한 경우만: 루트 유지
```

Git 로컬 정보는 `git rev-parse --absolute-git-dir`로 얻은 worktree별 디렉터리의 `petra/` 아래에 둔다. 캐시, 설치 중 백업, 이전 훅 주소는 원격에 올리지 않는다. `.git/sobaya/`는 Sobaya 소유이며 PETRA가 이동·복사·삭제하지 않는다.

**기존 프로젝트에는 예외를 둔다.** 기존 `collab/`는 이번 이전에서 그대로 두고 manifest에 `records: "collab"`로 기록한다. 구형 Sobaya의 `harness/sobaya.lock`도 기존 주소와 내용 그대로 둔다. 새 설치는 `records: ".petra/collab"`을 사용한다. 두 경로를 동시에 쓰지는 않는다. 코드 분리와 과거 기록 재배치를 한 번에 하지 않는 결정이다.

### 제작 저장소와 배포 파일

이 저장소의 README는 계속 PETRA 제작자·에이전트용이며 사람용 제작 안내는 `docs/guide.md`다. 소비 프로젝트의 README와 목적이 다르다.

- 제작 저장소에는 전체 테스트, 설계, 개발 저널을 유지한다.
- 소비 설치본은 릴리스별 명시적 파일 목록으로 만든다. 빈 claim·저널 양식은 포함하지만 팀의 실제 claim·저널, 테스트 fixture, PR 검토 기록은 포함하지 않는다.
- `docs/`, `tests/`, `scripts/`라는 폴더 이름만으로 설치·삭제 대상을 판정하지 않는다.
- 템플릿으로 생성한 새 리포를 정리할 때도 알려진 원본과 동일한 제작용 파일만 제거한다. 사용자가 수정하거나 새로 만든 파일은 보존하고 충돌로 보고한다.
- 정리 전 원본 커밋을 Git 이력에 남긴다. 이력 재작성이나 force push로 템플릿 흔적을 지우지 않는다.
- GitHub의 template 사용 경로는 유지한다. 설치기 하나를 빈 프로젝트·기존 프로젝트·템플릿 정리에 공통 사용하고 별도 구현을 세 개 만들지 않는다.

## 4. 파일 소유권과 업데이트

| 구분 | 예 | 설치·업데이트 규칙 |
|---|---|---|
| PETRA 관리 파일 | `runtime/`, `bin/`, `templates/`, `.petra/README.md`, `.petra/AGENTS.md` | 최초 설치 기준과 같을 때만 교체. 로컬 수정이면 중단하고 차이를 제시 |
| 프로젝트 파일 | 앱 코드, 루트 README, 실제 테스트, `.petra/config.sh` | 없을 때 초안 생성 가능. 이후 자동 교체 금지 |
| 공유 문서·설정 | 루트 AGENTS, 도구 설정, PR 양식, Git 훅, workflow, gitignore | PETRA가 추가한 부분만 변경. 다른 설정·명령·설명은 보존 |
| 프로젝트 기록 | claim, 저널, 보관한 plan | 코드 업데이트의 교체·청소 대상 아님. 기존 append-only 규칙 유지 |
| Sobaya 소유 | root pin, 구형 lock, 승인·연결·실행 상태, 외부 런타임 | PETRA 설치·업데이트에서 값·경로·버전 변경 금지 |

`manifest.json`이 설치 정보를 담는 유일한 기준이다. 별도 VERSION/lock에 같은 버전을 중복 저장하지 않는다. 최소 필드는 다음과 같다.

- `schema_version`, PETRA 릴리스 버전, 정확한 원본 커밋, 검토한 배포물 SHA-256.
- `records`: 위에서 정한 신규 또는 구형 기록 경로.
- `managed_files`: 리포 상대경로, 설치한 바이트의 SHA-256, 파일 종류와 실행 권한. 심링크를 사용하는 경우 대상도 비교한다.
- 공유 파일에 추가한 블록·설정 항목의 식별자와 설치 당시 값 또는 해시. 문서 전체 해시로 사용자 영역을 덮어쓰지 않는다.

개인 설치 경로, 토큰, 사용자 핸들, Git config의 개인 값은 manifest에 넣지 않는다. 경로는 허용된 리포 내부만 허용하며 `..` 또는 외부 심링크로 나갈 수 없다. 배포물의 해시 일치와 출처 신뢰를 같은 것으로 취급하지 않는다.

manifest는 `jq`로 단일 JSON 객체와 지원 schema를 검증한다. 원격 ref의 파일은 경로 선택을 위한 데이터로만 읽으며 shell 설정을 source하거나 그 ref의 설치 코드를 실행하지 않는다. 잘못된 manifest가 있는 ref를 조용히 구형 정상 ref로 취급하지 않고 확인 불가로 알린다.

같은 버전을 다시 설치하면 파일·권한·설정·mtime을 불필요하게 바꾸지 않는다. 이미 수정된 관리 파일은 덮어쓰기 옵션으로 밀어붙이지 않고 검토 후 해결한다. 업데이트는 명시적으로 선택한 릴리스에 한하며 세션 시작에 자동 교체하지 않는다.

## 5. 사람이 보는 설치 흐름

명령 표면은 아래 정도로 제한한다. 표의 명령은 아직 구현되지 않았다. 기존 협업 명령은 같은 진입점으로 전달하고 새로운 협업 절차를 만들지 않는다.

| 작업 | 목표 명령 | 결과 |
|---|---|---|
| 설치·기존 배치 이전 확인 | `sh <검토한 배포물>/bin/petra install --target <repo> --dry-run` | 만들기·연결·보존·충돌·제거 예정 목록만 출력 |
| 확인한 계획 적용 | 같은 명령의 `--apply` | 읽은 상태가 바뀌지 않았을 때 계획 적용. 수동 커밋·검토 대기 |
| 팀원 합류 | `sh .petra/bin/petra join <handle>` | 이 clone/worktree의 연결·핸들 준비. 공유 파일·원격 설정 변경 없음 |
| 설치 검증 | `sh .petra/bin/petra verify` | 파일·연결·기록 경로 점검. 프로젝트 테스트나 Sobaya gate를 대체하지 않음 |
| 일상 협업 | `sh .petra/bin/petra digest`, `pulse`, `check`, `run`, `worktree` 등 | 현재 협업 의미 그대로 |
| PETRA 업데이트 | 선택한 새 배포물의 `install --target ... --dry-run/--apply` | 같은 설치 계획기를 재사용. 별도 자동 업데이트 엔진 없음 |

### 새 쇼핑몰

1. 빈 Git 리포를 준비하거나 GitHub template에서 생성한다. 프레임워크를 먼저 만들었어도 기존 코드 위치는 유지한다.
2. 에이전트가 프로젝트 이름·핸들·실제 테스트 명령·필요한 도구 연결을 확인한다. 이미 알거나 설정된 값은 다시 묻지 않는다.
3. 설치기는 `.petra/`와 필요한 연결을 제안한다. 템플릿 그대로인 README는 쇼핑몰용으로 바꾸되, 아직 없는 실행·테스트 명령은 지어내지 않는다.
4. 적용·verify 후 바뀐 파일을 검토해 커밋한다. 새 GitHub 리포 생성·공개 여부·보호 정책 변경은 설치기가 몰래 하지 않는다.
5. solp와 amazon은 원래처럼 claim을 내고 저널을 읽는다. 사용자는 내부 디렉터리 이전 절차를 외울 필요가 없다.

### 이미 운영 중인 프로젝트

기존 README는 그대로 둔다. 루트 AGENTS에는 검토 가능한 작은 PETRA 구역만 제안한다. `scripts/`, `tests/`, `docs/`, `.github/`가 있어도 필요한 파일 단위로 처리한다. 같은 이름의 사용자 스킬이나 훅이 있으면 덮어쓰지 않는다. 구형 하네스가 있으면 아래 이전 절차를 선택하고 단순 신규 설치로 덮지 않는다.

### 팀원이 처음 clone했을 때

`.petra/`와 공유 설정은 Git으로 받는다. `join`은 로컬 연결만 준비하며 설치 버전을 바꾸지 않는다. Sobaya pin이 있으면 개인 저장소를 확인해 PR #5의 명시적 `sync` 절차로 안내한다. 기능 명세가 없는 main에서 `attach`나 승인을 만들지 않는다. 새 릴리스 자동 검색·알림은 #4에 추가하지 않는다.

## 6. AGENTS와 도구 연결

루트 `AGENTS.md`는 프로젝트 파일이다. 실제 `- Test:` 등 Sobaya 계약과 기존 규칙을 보존하고 다음과 같은 짧은 구역을 추가한다. 관리 마커 바깥의 내용을 다시 포맷하지 않는다.

```md
<!-- petra:begin -->
## PETRA 협업
파일을 수정하기 전에 `.petra/AGENTS.md`의 협업 계약을 읽는다.
세션 시작 시 `sh .petra/bin/petra digest --fetch`로 동료 상태를 확인한다.
작업 선언과 인수인계는 PETRA의 start-work·handoff 절차를 따른다.
계약 파일이나 명령이 없으면 설치 상태를 확인하고 사용자에게 알린다.
<!-- petra:end -->
```

`.petra/AGENTS.md`를 둔 것만으로 모든 세션이 이를 자동으로 읽는다고 가정하지 않는다. Codex는 리포 루트에서 작업 디렉터리까지의 지시문을 탐색한다. 따라서 루트에 참조와 핵심 시작 절차를 남기는 것은 이 설계의 선택이다. 근거: [공식 AGENTS 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

- 스킬은 기존 onboard·start-work·handoff의 세 절차만 유지한다. 새 설치의 이름은 `petra-onboard`, `petra-start-work`, `petra-handoff`로 충돌을 피한다. 구현 설명은 `.petra/`를 참조한다.
- 구형 스킬을 지울 때는 알려진 원본인지 확인한다. 수정된 사용자 스킬을 이름만 보고 삭제하지 않는다. 이전 세션은 전환 후 재시작한다.
- `.claude/skills` 전체를 새 심링크로 교체하지 않는다. 기존 실제 디렉터리·심링크를 조사하고 PETRA 항목만 연결한다.
- PR #3의 결정을 유지해 `CLAUDE.md`를 자동 생성하지 않는다. 기존 파일도 삭제하지 않는다. Claude의 실제 세션에서 공통 계약이 읽히는 경로를 검증하고, 확인되지 않은 환경은 수동 시작 경로로 표시한다.
- Claude와 Codex 설정 JSON이 비슷하다는 사실은 작동 증거가 아니다. 지원 버전·입력 이벤트·거부/문맥 전달 의미를 각각 확인해야 자동 연결을 제공한다. 이 설계 문서는 특정 Codex 훅 스키마의 지원을 확정하지 않는다.
- 미지원 환경에서는 AGENTS의 시작 명령과 같은 CLI·Git 훅·CI를 사용한다. 자동 편집 차단이 검증된 환경과 수동 환경의 보장 범위를 구분한다.

## 7. Git 훅과 CI

### Git 훅

`.githooks`는 안정된 외부 진입점으로 남긴다. 관리 훅 안에서 `.petra/bin/petra`를 호출하며, 현재 설치형 Sobaya가 가리키는 `.githooks` 주소와 전달 훅 메타데이터는 바꾸지 않는다.

- 기존 훅의 argv·stdin·cwd·환경·종료 상태를 보존한다. PETRA 검사와 사용자 훅, Sobaya 검사를 각각 한 번만 실행한다. 실패 후 다음 검사를 진행하지 않는다.
- 일반 프로젝트의 기존 hooksPath를 무조건 `.githooks`로 교체하지 않는다. 이전 주소는 로컬에 보존하고 검토된 연결을 구성한다. 체인을 안전하게 만들 수 없는 경우 충돌로 중단한다.
- Sobaya 설치형 연결이 이미 있으면 외부 전달 훅을 감싸거나 재생성하지 않는다. 원본 `.githooks` 내부의 PETRA 관리 코드만 교체한다. 다른 hooksPath의 새 프로젝트는 먼저 일반 훅 연결을 검증한 뒤 별도로 Sobaya attach를 진행한다.
- Git 설정을 읽거나 잠시 바꿀 때 원래 local/worktree 범위와 값의 존재 여부까지 보존한다. 전역 설정은 바꾸지 않는다. 단순 경로 문자열 교체로 해결하지 않는다.
- 다른 worktree의 승인·훅·config는 그대로여야 한다. 경로가 바뀌는 `git worktree move` 이후에는 verify로 재연결 필요 여부를 안내하며 자동 정상으로 간주하지 않는다.

### CI와 PR

제작 저장소는 기존 전체 테스트와 신규 설치·이전 테스트를 돌린다. 소비 프로젝트에는 PETRA 자체의 전체 테스트나 Sobaya 릴리스 테스트 자산을 복사하지 않는다. 소비자 workflow는 설치·연결 smoke 검사와 해당 PR의 협업 검사만 실행하고 앱 테스트는 기존 앱 CI가 맡는다.

- 첫 전환에서는 required check 이름 `훅·루프 검증`, `협업 규칙 검사`를 유지한다. 전자는 소비자 배치와 훅 진입점의 smoke 검증이며 제작자의 전체 테스트와 구분한다.
- 기존 PETRA workflow를 교체할 때 원본 또는 관리 영역이 확인되어야 한다. 같은 check를 내는 구형 workflow가 함께 남지 않게 계획한다. 사용자 수정이 섞였으면 수동 검토한다.
- 실제 GitHub에서 두 check가 생성되는지 확인하기 전에는 기존 보호를 제거하지 않는다. 설치기는 보호 정책을 자동으로 덮어쓰거나 이미 요구되는 앱 CI를 누락시키지 않는다.
- 1인 이상 승인, 새 커밋 재승인, 대화 해결, main 직접 push 금지 등 팀이 정한 정책을 유지한다.
- PR 양식이 있으면 PETRA 구역만 추가한다. `check`, `pr-body`, claim 정리, plan 보관은 설정된 기록 경로를 사용해야 한다.
- 기존 정리 자동화의 설정은 별도 소유권 검사 후 옮긴다. 설치하면서 새 auto-merge나 강제 push 동작을 켜지 않는다.

## 8. 이전과 업데이트의 적용 절차

### 사전 조건

소비 리포에서 별도 작업 브랜치를 사용한다. 작업 트리·인덱스가 깨끗하고 merge/rebase가 진행 중이지 않아야 한다. 현재 worktree에 살아 있는 Sobaya 실행·관리 잠금이나 active 항목이 있으면 이전을 거부한다. 동료에게는 작은 전용 PR로 범위와 전환 시점을 알린다.

첫 구현에서는 **등록된 다른 linked worktree가 있는 저장소의 구형 배치 이전을 거부**한다. 공유 config 변경이 각 worktree에 미치는 영향을 자동 해결하지 않는다. 다른 worktree의 작업을 삭제·중단시키지 않고, 완료 후 사람이 정리하거나 별도 검토하는 경로를 안내한다. 연결 주소를 바꾸지 않는 일반 업데이트의 다중 worktree 지원은 수용 테스트로 따로 검증한다.

### 읽기 전용 계획

1. Git 루트, 파일·권한·심링크, hooksPath의 scope, 기존 하네스 버전, pin, 활성 상태를 조사한다.
2. 신규 설치/정확히 같은 버전/업데이트/구형 배치/충돌 중 하나로 분류한다. 알 수 없는 하네스를 버전 문자열만 믿고 삭제하지 않는다.
3. `생성`, `교체`, `연결`, `보존`, `제거`, `수동 확인`의 파일별 목록을 보여준다. dry-run은 Git 설정·캐시·외부 런타임까지 바꾸지 않는다.
4. 적용은 같은 배포물·대상·옵션의 계획을 다시 계산하고 확인한 계획과 비교한다. 적용 직전에 파일과 설정도 다시 비교한다. 그 사이 변경되었거나 계획에 충돌이 있으면 쓰기 전에 중단한다.

### 적용과 실패 복구

1. worktree별 설치 잠금을 확보하고 작업 중 표시와 바꿀 파일·로컬 config의 백업을 Git 메타데이터에 둔다. 이 잠금은 설치 때만 사용하며 평소 협업 훅을 늘리지 않는다.
2. 대상과 같은 파일시스템에서 후보 배치를 준비하고 검증한다. 실행 경로, 권한, 연결 누락을 먼저 확인한다.
3. 관리 대상 파일과 연결을 반영한다. verify까지 성공한 뒤 manifest를 최종 기록하고 설치 중 표시를 제거한다. 다중 파일 변경을 원자적이라고 표현하지 않는다.
4. 실패하면 이번 작업이 실제로 바꾼 경로·config만 백업으로 복구한다. 복구 중 예상과 다른 변경을 발견하면 덮지 않고 백업과 진단을 남긴다. `reset --hard`, 전체 디렉터리 삭제, 자동 stash/커밋은 사용하지 않는다.
5. 중단 흔적이 남으면 다음 verify/join은 불완전 설치를 알린다. 공유 파일을 바꾸는 복구는 사람이 확인한 계획으로 진행하며 join이 몰래 수행하지 않는다.

설치·이전·업데이트는 자동 커밋·push·승인·머지를 하지 않는다. 결과 diff를 검토해 일반 PR로 공유한다. 버전 롤백도 같은 소유권 검사와 검증을 거치는 별도 PR이며, 저널·개인 설정·Sobaya 승인 상태를 과거로 되돌리지 않는다.

### 구형 배치의 특별 규칙

- 옮기는 것은 입증된 PETRA 코드·사용 문서다. 앱의 `scripts/`, `tests/`, `docs/`는 이름이 같아도 소유하지 않는다. 알려진 배포 파일 목록에 있는 원본 해시로 확인한다.
- 기존 `collab/`의 파일 바이트·파일명·Git 이력은 유지한다. 오래된 문서의 링크를 고치겠다고 저널을 다시 쓰지 않는다. manifest의 기록 경로를 사용하고 새 양식은 `.petra/templates/`에서 가져온다.
- `harness/sobaya.lock`은 남긴다. 삭제해서 설치형으로 전환하지 않는다. 구형 어댑터만 `.petra/runtime/`로 옮기고 예전 lock 주소를 읽게 한다.
- 이전 PR은 append-only 검사나 claim 소유권을 통째로 우회하지 않는다. 코드 이동을 위해 데이터 검사를 끄는 예외를 추가하지 않는다.
- 열려 있는 옛 브랜치의 `collab/` 기록을 읽고 현재 기록과 중복 제거할 수 있어야 한다. 새 배치의 ref는 그 ref의 manifest를 보고, manifest 없는 ref는 기존 `collab/`로 읽는다. 각 ref당 기록 위치는 하나만 선택한다.
- 옛 에이전트의 무변경 호환까지 보장하지 않는다. 이전 PR 머지 후 기존 작업자는 개발 루프를 멈춘 안전한 시점에 main을 merge하고 join·verify 후 세션을 다시 연다. 구형 CLI 주소를 무기한 유지하는 별도 구현은 만들지 않는다.
- 기록까지 `.petra/collab/`로 옮기는 작업은 이후 팀 전체의 별도 전환이다. 이번 구현의 완료 조건이 아니다.

## 9. 소바야 및 내부 경로의 구현 접점

| 현재 지점 | 필요한 변경 |
|---|---|
| `find_root_from`, 각 스크립트의 `dirname` 계산 | Git 프로젝트 루트와 PETRA 코드 위치를 구분. `.git`이 파일인 worktree와 하위 디렉터리 실행도 지원 |
| `CLAIM_DIR`, `JOURNAL_DIR`, 원격 journal 조회 | ref별 manifest의 기록 경로를 사용. 구형 ref는 `collab/` fallback |
| WIP·my_files·scope 관련 경로 제외 | 저널 저장소와 설치용 메타데이터를 앱 코드와 구분. 두 배치에서 같은 파일 겹침 결과 |
| 캐시 | worktree별 Git 메타데이터로 이동. 캐시 재생성은 가능하나 미응답 질문을 유실시키지 않음 |
| 훅, 스킬, PR 양식, CI, root dispatcher | 동일한 PETRA 진입점을 참조. 실행 정책의 복사본을 만들지 않음 |
| 구형 `attach-sobaya.sh` | scope 보존 회귀 수정 유지, 구형 lock 경로 보존, 설치형으로 자동 전환 금지 |
| 설치형 어댑터와 `si_connection` | 새 코드 위치에서 동작하되 `.githooks` 원본 주소·forwarder·연결 JSON·root pin은 유지 |
| `run`, `worktree`, `pr-body`, handoff | 동료 허브 파일 검사, 살아 있는 잠금 보류, 리뷰 HEAD 기록, plan 보관 규칙 유지 |
| 설치기·패키징 | 전체 source 복사 대신 배포 allowlist. 기존 init의 전역 치환과 lock 삭제를 호출하지 않음 |

Sobaya `spec.md`, `failed-test.md`, `sobaya.json`, `sobaya.lock`, 실제 `AGENTS.md`의 위치는 소바야 계약을 따른다. PETRA가 위치를 정리하려고 이 계약이나 사용자 승인 입력을 바꾸지 않는다. 설치형 저장소와 구형 소스 클론은 계속 프로젝트 밖에 두며 `.petra/`로 복사하지 않는다.

## 10. 구현 순서와 확정 기준

| 단계 | 산출물 | 시작/완료 조건 |
|---|---|---|
| 지금 | 이 설계와 수용 테스트 목록 | 문서만 공유. 실행 코드·버전·PR #5 변경 없음 |

A/B는 검토 가능한 구현 단위다. 실제 PR 개수는 diff 크기에 맞추되 둘 중 일부만 구현한 상태를 #4 전체 완료로 표시하지 않는다. 신규 생성만 지원하는 중간 릴리스라면 기존 사용자 이전 미지원이라고 분명히 알린다.

선택을 보류하지 않고 이 문서에서 제안하는 기준은 `.petra/`, 관리 파일과 사용자 파일의 분리, Git으로 버전을 공유하는 설치본, 기존 기록·lock 보존, PR #5 이후 구현이다. 팀의 최종 승인 기록은 아직 없다. 세부 도구 어댑터 지원 버전은 실행 검증 결과로 확정한다.

구체적인 합격 조건은 [수용 테스트 계획](petra-acceptance.md)에 있다. 새 동작은 아직 구현하거나 시험하지 않았으므로 이 문서 자체를 통과 증거로 쓰지 않는다.
